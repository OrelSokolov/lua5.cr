# lua5.cr — план бенчмарков

Бенчмарки здесь не «похвастаться цифрой», а решить три задачи:

1. **Регресс-трекинг** — изменения интерпретатора не должны незаметно
   замедлять его. Результаты фиксируются в JSON, сравниваются с базой.
2. **Точки фаз** — PLAN.md идёт AST-интерпретатор → VM → JIT. Один и тот же
   набор на каждой фазе даёт измеримый ответ «VM быстрее интерпретатора
   в X раз, JIT — в Y». Это критерий успеха фаз 3 и 5.
3. **Сверка с референсами** — LuaJIT (jit on и jit off) и Lua 5.1 на тех же
   скриптах. Не чтобы догонять (мы не догоняем, см. PLAN), а чтобы видеть
   реальный зазор и понимать, где мы теряем больше всего.

## Референсы

| Референс        | Зачем                                            |
|-----------------|--------------------------------------------------|
| `luajit`        | верхняя планка производительности               |
| `luajit -j off` | интерпретатор LuaJIT — честный «интерпретаторный» ориентир |
| `lua5.1`        | исторический базлайн (то, на чём работала GSC)   |

Все результаты нормализуются к `luajit -j off` = 1.0, рядом печатаются
абсолютные секунды. Нормализация к LuaJIT-*интерпретатору* честнее, чем к
JIT: наш VM — тоже интерпретатор, и сравнение «интерпретатор с
интерпретатором» показывает качество диспетчеризации, а не отсутствие JIT.

## Методика измерений

### Время: внешний wall-clock

- Harness запускает **исполняемый файл** (`bin/lua5`, `luajit`, `lua5.1`)
  с бенч-скриптом и меряет время процесса по `Clock.monotonic`.
  Один и тот же механизм для всех VM — сравнение честное.
- **Калибровка пустого скрипта**: время запуска `return` вычитается
  (стартовый оверхед у нас заведомо больше — Crystal-рантайм инициализируется
  дольше C-шного).
- Внутри скрипта — сам hot-loop и `os.clock()` в конце; harness сверяет
  внутреннее и внешнее время (расхождение > 10% = подозрение на I/O или
  зависание в рантайме).

### Статистика

- Каждый бенч: **1 прогрев + N запусков** (N = 5 по умолчанию).
- Отчёт: `min` и `median`; `min` — основная метрика (стандарт Benchmarks
  Game: минимум = наименьший шум), median — sanity-чек.
- Коэффициент вариации > 5% → результат помечается `unstable`, в сравнении
  с базой не участвует.
- Длительность бенча подбирается так, чтобы на самом быстром референсе
  (`luajit`) было **не меньше 0.1 с** — иначе меряем гранулярность таймера
  и оверхед запуска процесса.

### Контрольный checksum (guard корректности)

Каждый бенч-скрипт накапливает результат вычислений (сумма float или хеш
строк) и печатает `CHECKSUM <значение>` последней строкой. Harness
сравнивает checksum между **всеми** VM. Расхождение = бенч FAILED, а не
«медленный результат»: бенч, который считает не то, что референсы,
скорость не меряет. Это продолжение диф-тестов из PLAN.md, но на
производительных скриптах.

### Окружение (Linux)

- Сборка только `crystal build --release --no-debug`. Debug-сборка
  в результатах помечается и отбрасывается.
- `taskset -c <core>` — фиксированное ядро, не #0 (там прерывания).
- Говернор `performance`, ноутбук от сети. Turbo отключить без root не
  выйдет — просто зафиксировать: окружение записывается в JSON результата
  (CPU, governor, сборка, дата) и сравнивать «сегодня против базы» имеет
  смысл только на одной машине.
- В горячем цикле — **ноль I/O** (`print` только checksum в конце).
- `math.randomseed(42)` в начале каждого скрипта, если random используется.

На macOS (нет `timeout(1)` и `/proc`) harness сам переключается на
spawn + KILL по дедлайну и `sysctl` для CPU-строки; референсы собираются
локально в `bench/vendor` (`lua-5.1.5` из tarball lua.org, LuaJIT —
`make install PREFIX=bench/vendor/luajit`, для сборки нужен
`MACOSX_DEPLOYMENT_TARGET=$(sw_vers -productVersion)`).

## Набор бенчмарков

Лежат в `bench/*.lua`, один файл = один бенч. Текст скрипта **идентичен**
для всех VM (чистая семантика 5.1, никаких `jit.*`).

### Micro — изолированные операции

| Файл            | Что нагружает                                                     |
|-----------------|-------------------------------------------------------------------|
| `call.lua`      | вызов функции (0/3 аргумента), хвостовая рекурсия                 |
| `arith.lua`     | int/double арифметика, сравнения                                  |
| `str.lua`       | конкатенация `..`, `string.format`, `string.rep`                  |
| `table.lua`     | создание таблиц, array-часть vs hash, вставка/удаление            |
| `closure.lua`   | замыкания, upvalue-мутации                                        |
| `meta.lua`      | `__index` (таблица/функция), `__add`, `__call`, `__eq`            |
| `patterns.lua`  | `gsub`/`gmatch`/`find` на ~100 КБ текста — движок паттернов lstrlib |
| `varargs.lua`   | `select('#', ...)`, `unpack`, varargs-проброс                      |
| `sort.lua`      | `table.sort` с компаратором (стресс на колбэки из VM)             |

### Kernels — классика Benchmarks Game / lua-benchmarks

| Файл               | Что нагружает                          |
|--------------------|----------------------------------------|
| `nbody.lua`        | double-математика, массивы             |
| `binary-trees.lua` | аллокации таблиц + GC                  |
| `fannkuch.lua`     | целочисленные циклы, массивы            |
| `spectral.lua`     | вложенные циклы, вызовы                |
| `mandelbrot.lua`   | tight numeric loop                     |
| `nsieve.lua`       | битовые операции, большие таблицы      |
| `matrix.lua`       | naive умножение — двойная индексация   |
| `jsonish.lua`      | сериализация глубокой таблицы в строки — типичная игровая нагрузка |

Источники кода — github.com/keplerproject/lua-benchmarks (реальные,
давно обкатанные), lua-users wiki (LuaPerformance-страница) и порты
Benchmarks Game, с адаптацией под чистую 5.1 и одинаковые warmup-петли.

### Macro — «игровые» сценарии

То, ради чего проект существует. Пишем сами, по мотивам реальной нагрузки
xray-16 (`db.storage`/xr_logic, script_callback_ex, luabind-классы,
news_manager, task_manager, корутины модов). Лежат в `bench/xray/`,
harness ищет скрипт сначала там, потом в vendor-наборе. «Рандом» —
чистый LCG в Lua (последовательности `math.random` у PUC Lua и LuaJIT
не совпадают → checksum разъедется), вывод детерминирован и одинаков
на всех VM.

| Файл            | Сценарий                                                                       |
|-----------------|--------------------------------------------------------------------------------|
| `xr-update.lua` | «кадр» smart-terrain: `db.storage[npc_id]`, pairs-перебор, фильтрация, апдейты, выбор цели сканом, delete/insert (rehash) |
| `events.lua`    | диспетчер колбэков (аналог `script_callback_ex`): тысячи замыканий, подписка/отписка на лету, string-keyed lookup |
| `oop.lua`       | иерархия `Entity → NPC → Stalker` / `Monster` на `setmetatable`: полиморфные вызовы, super, методы через 3 уровня `__index` (аналог luabind-классов) |
| `spawn.lua`     | churn мелких таблиц: hash+array+вложенная+строка, кольцо «долго живущих», остальное в GC (контраст с binary-trees: много мелкого) |
| `news.lua`      | строковая нагрузка HUD/новостей: `string.format`, каскады `..`, `gsub`-плейсхолдеры, `rep/sub/find` |
| `sort-queue.lua`| приоритетная очередь task_manager'а: `table.sort` с компаратором на записях, смена приоритетов, insert/remove |
| `veclib.lua`    | векторная математика на `{x,y,z}`: шаг физики, дистанции, нормализация (только IEEE-детерминированные ops, без sin/cos) |
| `coro-mgr.lua`  | менеджер корутин-таймеров (отложенные действия модов): create/resume/yield, расписание пробуждений |

### Не-исполнение: парсинг и старт

- **`parse.lua.bench`**: lex+parse большого файла (склейка conformance
  + kernels, ~1 МБ) **без исполнения** (`loadstring` в цикле, результат
  отбрасывается). Метрика — МБ/с. Парсер от VM не зависит — меряем уже
  сейчас и на каждой фазе (регрессии лексера/парсера отдельно видны).
- **Холодный старт**: время `bin/lua5 -e "return"` vs `luajit -e "return"`.
  Для launcher/плагинов (PLAN, фаза 5) это отдельная важная метрика.

### Память

- Peak RSS: чтение `/proc/self/status` → `VmHWM` в конце harness-обёртки
  (или `/usr/bin/time -v` как кросс-VM вариант).
- Для Crystal-VM дополнительно размер кучи Boehm (`GC` heap stats), чтобы
  ловить утечки реестров/замыканий между запускам внутри процесса.
- Память меряется на kernels (binary-trees — главный), micro не нужны.

## Harness

```
bench/
  *.lua              # бенч-скрипты (общие для всех VM)
  run.cr             # harness: запуск, тайминг, checksum, JSON
  results/           # <дата>_<vm>.json + env-запись
  base.json          # зафиксированная база для регресс-сравнения
```

Команды (через `make` / shard task):

- `make bench` — текущая VM, все бенчи, N=5, пишет `results/`.
- `make bench-all` — то же + `luajit`, `luajit -j off`, `lua5.1`.
- `make bench-cmp` — diff против `base.json`; порог: замедление > 5%
  на стабильном бенче = FAIL (быстрее — не FAIL).
- `make bench-base` — перезаписать базу текущими результатами (явно, руками).

JSON на бенч: `{name, vm, min, median, cov, checksum, rss, env}`,
env один на файл прогона.

Harness не измеряет ничего внутри Lua — только вокруг процесса.
Вся логика статистики и сравнения на Crystal, чтобы не дублировать её
на трёх VM.

## Правила против мусорных результатов

- Скрипт чистой 5.1; никаких `pcall` вокруг горячего цикла (кроме бенчей
  ошибок — таких в наборе нет).
- Не сравнивать между машинами / после смены governor — только base.json
  с той же машины.
- Один бенч = одна метрика. «Пофигурист» (сортировка + паттерны + строки
  в одном файле) ничего не локализует.
- Micro-бенчи не суммируются в «общий балл» — только по-отдельности;
  сводный график — kernels normalized к `luajit -j off`.
- Результат без записанного env не принимается.

## Этапы (привязка к фазам PLAN.md)

1. **Сейчас (фаза 1)**: harness + micro + kernels + parse-бенч; первый
   прогон `bench-all` — фиксация точки AST-интерпретатора. Ожидание:
   в разы медленнее `luajit -j off` — это норма и не баг; важно, ЧТО
   именно медленнее (micro покажут: диспетчер, аллокации, паттерны).
2. **Фаза 3 (VM)**: тот же набор без изменений. Метрика — ratio
   `vm / interp` по каждому бенчу. DoD фазы 3 по скорости: kernels
   ускорились не менее чем в 2-3 раза; где нет — разбираться, что в
   AST-walkerе мешало (обычно — смена Value-представления и аллокации Env).
3. **Фаза 5 (JIT)**: ratio `jit / vm`, отдельно на kernels (должен расти)
   и на macro (колбэки/метатаблицы — обычно растёт слабее; это ожидаемо).
4. Macro-бенчи (`oop`, `events`, `sim`, `tasks`) — добавляются в фазе 1/2
   по мере роста stdlib, до VM: к моменту фазы 3 набор должен быть полным.
