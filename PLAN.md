# lua5.cr — план

Полный интерпретатор Lua 5.1 (+ расширения LuaJIT) **на Crystal**, без нативного
Lua и без C-слоя вообще. Цель — не «ещё один Lua», а **luabind к Crystal-объектам**:
скрипты дергают Crystal-классы напрямую, через макросы и компайл-тайм рефлексию,
с общим GC и общей моделью исключений. C-API (`lua_State`, стек, `lua_push*`)
не реализуется принципиально — он и есть источник класса багов, от которого
уходим (сравни: SIGSEGV в `strcmp` при `alife():object(nil)` — типичный баг
C-границы, здесь невозможен по построению).

Стратегия — **порт MoonSharp (C#) модуль за модулем**, не изобретаем свои
решения: MoonSharp прошёл этот путь (AST-интерпретатор → байткод-VM →
interop-слой) и его структура почти один-в-один ложится на Crystal.

## Фазы

### Фаза 0 — каркас ✅
shard-проект, CLI `bin/lua5`, spec-раннер conformance-файлов.

### Фаза 1 — MVP (совместимость семантики) ✅
- Лексер 5.1 (+ `\x`/`\z` из LuaJIT), парсер полного грамматики 5.1.
- AST-интерпретатор: замыкания/upvalue (через Env-цепочку с Cell), varargs,
  множественные возвраты/присваивания, хвостовые вызовы (trampoline по
  TailCall-сигналу — глубокая рекурсия `return f()` не переполняет стек).
- Метатаблицы: `__index`/`__newindex` (цепочки, table|function), арифметика,
  `__concat`, `__eq`, `__lt`/`__le` (+ fallback `not (b < a)`), `__len`,
  `__call`, `__tostring`, `__unm`, protected metatables.
- stdlib: base (pcall/xpcall/error с уровнями, select/unpack, next/pairs/
  ipairs, setmetatable, loadstring, assert, tonumber с базой), math (вкл.
  fmod/modf/random), table (insert/remove/concat/sort), string: базовые +
  **полный порт движка паттернов lstrlib** (классы, множители, `%b`, `%f`,
  backrefs, позиционные и пустые захваты, find/match/gmatch/gsub, plain),
  string.format (d/i/x/o/e/f/g/s/q/c, флаги, `*`), минимальный os.
- Interop-срез: макрос `expose` + аннотация `@[LuaMethod]`, оборачивание
  Crystal-объекта в userdata с методами; конвертация аргументов по
  ограничениям типов. Полный слой — фаза 4.
- Conformance-набор `.lua` в spec/conformance/.

DoD фазы 1: все conformance-файлы зелёные; `return f()`-рекурсия 1e6 итераций
без переполнения стека; типичный SoC-скрипт с ООП (`setmetatable(t, {__index=...})`)
выполняется.

### Фаза 2 — добивка 5.1/LuaJIT
- os.date/time полный, io (минимальный), debug-библиотека (getinfo/traceback
  по нашим AST-строкам — сюда же `chunkname:line` в ошибках).
- require/dofile с загрузчиком путей (аналог MoonSharp Loaders).
- goto/labels (5.2/LuaJIT), целочисленное деление `//`, `\u{XXX}`? — только
  то, что реально использует LuaJIT в режиме 5.1+ext.
- Полный прогон lua5.1-tests (lua.org); расхождения — чинятся до перехода
  к фазе 3.

### Фаза 3 — байткод-VM (порт MoonSharp Execution/Vm)
- Компиляция AST → свой байткод, switch-цикл диспетчеризации. ✅
  Исполнение — упакованный 64-битный формат (op:8 | a:16s | b:20s | c:20s),
  `Proto#packed` — фикс-энкодинг, который будет читать и JIT (фаза 5).
- **Представление значения — исследование закрыто (2026-11)**: union-алиас
  Crystal УЖЕ является tagged-layout'ом фиксированных 16 байт
  (type_id + payload); hand-written `struct Value` с tag+полями выходит
  24–32 байта — хуже. NaN-boxing (8 байт) для интерпретаторных контейнеров
  заблокирован Boehm GC: указатель, спрятанный в NaN-паттерне,
  консервативный сканер не видит → преждевременный сбор. Вывод: для
  скорости интерпретатора смена представления ничего не даёт; боксинг
  решается на этапе JIT — там значения живут в регистрах небоксированными
  и на стек подчинён дисциплине кадра JIT (см. «JIT», п. 2).
- Корутины: value-stack на корутину (не Crystal-файберы) — порт семантики
  `resume`/`yield`/wrap, включая yield через метаметоды (в 5.1 запрещён —
  честная ошибка).
- Интерпретатор не удаляется: он fallback навсегда.

### Фаза 4 — Interop: полный luabind (порт MoonSharp Interop/)
- Аннотации: классы/методы/свойства/конструкторы, наследование Crystal-классов,
  видимое из Lua (`__index`-цепочки на userdata-обёртках).
- Конвертеры типов в обе стороны (Int32/64, Float, String, Bool, nilable,
  Array→table и обратно), автоматические и переопределяемые.
- Перегрузки: runtime-диспетчер по типам аргументов на стеке (как в
  luabind `match_signature`).
- Модель ошибок: Lua-ошибка — Crystal-исключение и наоборот, без потерь
  типа (error(table) доезжает до pcall той же таблицей).

### Фаза 5 (опционально) — JIT
См. раздел «JIT» ниже. Отдельно решаем: нужно ли вообще (для launcher/плагинов
скорости VM хватает).

## JIT: что заложить СЕЙЧАС, чтобы прикрутить потом

Кодогенерация в мире «только Crystal, ноль C»:

1. **Субстрат** — байткод-VM из фазы 3. JIT компилирует горячие байткод-функции.
   К AST-walker JIT не прикручивается, поэтому фаза 3 обязательна.

2. **Представление значения** — `struct Value` фиксированного размера (фаза 3).
   Сгенерированный код читает тег и payload напрямую; если значение размазано
   по Crystal-объектам — дешёвой проверки типа нет и JIT теряет смысл.

3. **Граница вызова** — через Crystal `fun` (extern, C-конвенция). Это НЕ
   «C-слой»: ни строчки кода на C, вся логика в Crystal, `fun` — только
   объявление сигнатуры, по которой машинный код зовёт рантайм-хелперы
   (аллокация таблицы, вызов метаметода, tonumber и т.п.). Обычные `def`
   из JIT не вызывать никогда: ABI обычных методов Crystal не стабилизирован.

4. **Исключения/ошибки** — Crystal-исключения НЕ разматываются сквозь
   JIT-фреймы (landing pads/personality — не наша епархия). Ошибка идёт
   кодом возврата по JIT-фреймам (как в VM), в Crystal-исключение
   конвертируется на внешней границе вызова. С фазы 3 ошибки в VM-цикле
   тоже переводим на коды возврата — единая механика.

5. **GC** — аллокации только через runtime-хелперы (fun-обёртки над Crystal
   аллокатором). Boehm сканирует стек/регистры консервативно: значения в
   JIT-фреймах он видит без нашей помощи, донастройка не нужна.

6. **Кадры вызовов** — сосуществование интерпретируемых и JIT-фреймов в обе
   стороны; layout кадра фиксируется в фазе 3 (стек значений в кадре —
   просто массив Value). Корутины: JIT и переключение корутин = проблемы
   stitching, как у LuaJIT; корутины продолжают исполняться интерпретатором
   (запрет JIT в корутинах — приемлемое v1-ограничение).

7. **Реализация эмиттера** — выбор в фазе 5:
   - **LLVM ORC** через llvm-шард: генерируем IR, конвенции/unwind берёт
     на себя LLVM; рантайм-зависимость на LLVM-библиотеки (Crystal сам
     LLVM-инструментирован — не чужеродно).
   - **Свой эмиттер** (DynAsm-стиль): байты опкодов + mmap/mprotect;
     ноль зависимостей, но x86-64 и AArch64 пишем руками.

Ожидания: интерпретатор на Crystal — нативный код, это не «интерпретатор
интерпретатора»; JIT даёт выигрыш относительно НАШЕГО интерпретатора/VM.
Гоняться с LuaJIT не цель — цель полная семантика + нативный luabind.

## Тестирование

- `crystal spec`: юнит-тесты лексера/парсера/интерпретатора + conformance
  `.lua`-файлы (spec/conformance/*.lua — assert-based, прогон через bin/lua5).
- Диф-тестирование против системного luajit (где установлен): один файл →
  два прогона → diff stdout. Ловит расхождения форматирования чисел,
  паттернов, ошибок.
- Каждая фаза заканчивается прогоном lua5.1-tests (github.com/lua/lua,
  ветка 5.1, test/) с зафиксированным списком известных расхождений.

## Риски / принципы

- Строки — байты, не UTF-8 (все строковые операции байтовые).
- Числа — только double (семантика 5.1), печать `%.14g`.
- `error()` с таблицей/числом доезжает до pcall как есть (без tostring).
- Порядок `pairs` — insertion order Crystal-хеша (Lua не специфицирует;
  фиксированный порядок лучше, чем рандом, для диф-тестов).
- AGENTS-правило переносится сюда: никаких тихих деградаций — незнакомая
  конструкция = громкая ошибка, а не пустой результат.
