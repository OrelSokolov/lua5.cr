# lua5.cr — план JIT (фаза 5 PLAN.md)

Документ — рабочий план Just-in-Time компилятора. Основан на текущем
состоянии VM (не на предположениях) и на закрытых исследованиях
представления значений (см. PLAN.md, фаза 3).

## 1. Архитектурные решения

### 1.1 Гранулярность — функция, не trace (v1)

Компилируем **целые прототипы** по счётчику горячести (стиль LuaJIT 1.x /
RaptorJIT), а не трейсы. Причины: проще bailout, нет trace-linking
специфики, предсказуемая память. Trace-компилятор и OSR — v2 (M6).

### 1.2 Тиринг

1. Интерпретация; в inline-CALL инкрементируется счётчик замыкания.
2. Порог (по умолчанию ~500 вызовов, настраивается) → компиляция.
3. `LuaClosure` получает поле `@compiled : Pointer(Void)?`; CALL в VM
   проверяет его (один branch на вызов) и уходит в машинный код.
4. Deopt/редкие пути → возврат в интерпретатор с восстановлением кадра.

### 1.3 Представление значений в JIT-коде

- Числа — **небоксированные** double в FP-регистрах (главный выигрыш
  над интерпретатором: union-трафик 16 байт исчезает).
- Ссылки (String/Table/Closure/…) — указатель + тег-гвард на загрузке.
- **Инвариант GC (v1)**: все живые Lua-значения лежат в слотах окна кадра
  в общем `Interp@stack`; регистры держат значения только между
  точками, где возможна аллокация/вызов хелпера. Перед любым вызовом
  хелпера значения записываются обратно в слоты. Тогда Boehm видит все
  корни консервативно (стек сканируется) + значение-стек — как сегодня.
  Никакого NaN-boxing в JIT-кадрах: указатель в регистре/spill виден
  консервативному сканеру и так; прятать его нельзя.

### 1.4 Ошибки — коды возврата, не исключения

- Рантайм-хелперы возвращают статус; JIT-функции размножают ошибку
  кодом (в r0/x0), Crystal-исключение `LuaError` создаётся только на
  границе входа (в `Interp#call`), где unwind безопасен.
- Требование: перевести **хелперы, вызываемые из JIT** (не весь VM),
  на коды возврата. Полный перевод VM-цикла на коды — опционально.

### 1.5 Вызов рантайма — только через `fun`

JIT-код зовет Crystal только через `fun` (C-конвенция): аллокация
таблицы/строки/замыкания, медленный gettable/settable, метаметоды,
tonumber, конкатенация, вызов интерпретируемой функции, ошибка.
Обычные `def` — никогда (ABI Crystal нестабилен). Таблица хелперов
закреплена в `src/jit/runtime.cr` как `@[Externa]`-набор с стабильными
адресами, JIT эмитит прямые call'ы.

### 1.6 Эмиттер — LLVM ORC (v1), свой AArch64 (v2)

- **v1: LLVM ORC** через llvm-шард: генерируем LLVM IR, кодоген и
  calling conventions — их. Риск: совместимость версии шруда с
  системным LLVM — проверить в M1 первой же задачей; несовместимость =
  переход на план Б.
- **v2 (M6): свой эмиттер** в стиле DynAsm (по примеру LuaJIT):
  байты опкодов AArch64 + mmap/mprotect. Ноль зависимостей, полный
  контроль, но кодировки x86-64/AArch64 руками.
- Конвейер (hotness, guards, deopt, рантайм-API) проектируется
  **эмиттер-агностично**: IR-билдер — тонкий слой, дублируемый эмиттером.

### 1.7 macOS (основная платформа разработки)

- `mmap(MAP_JIT)` + `pthread_jit_write_protect_np(false/true)` вокруг
  записи кода (W^X); для безхардened-процесса (обычный CLI-бинарь)
  исполнение JIT-страниц разрешено.
- AArch64 — целевая архитектура; x86-64 для v2-эмиттера.

## 2. Кодогенерация (что компилируем)

Все опкоды байткода делятся на классы:

| Класс | Примеры | Стратегия |
|---|---|---|
| Чистая арифметика | ADD..POW, LOADK, MOVE, JMP/JMPF/JMPT | прямой код, тег-гварды на операндах, double в FP-регистрах |
| Сравнения | EQ/NEQ/LT/LE | fast-путь инлайн, mismatch → deopt-гвард или хелпер |
| Табличный доступ | GETTABLE/SETTABLE/SELF | v1: хелпер + inline-кэш под константный строковый ключ (M3) |
| Вызовы | CALL/TAILCALL | JIT→JIT прямой; JIT→interp через хелпер; хот-колл инлайн (M5) |
| Циклы | FORPREP/FORLOOP | развёрнутый код + счётчик итераций (для OSR в v2) |
| Аллокации | NEWTABLE/SETLIST/CLOSURE | хелперы |
| Редкое | VARARG(мульти), CONCAT длинный, метаметоды | хелперы или deopt |
| RETURN | RETURN | запись результатов в слоты кадра, возврат по конвенции |

Типовая обратная связь (M3): интерпретатор на горячем участке
семплирует типы операндов per-pc (битовая маска в side-таблице Proto),
JIT специализирует код по наблюдённым типам + гварды. Спекуляция
ошиблась → deopt, маска расширяется, перекомпиляция.

## 3. Deopt

- Гвард провалился → `jit_deopt(interp, closure, pc, frame_layout_id,
  spill…)` хелпер: восстанавливает кадр интерпретатора в `@stack`
  (значения уже в слотах по инварианту 1.3), ставит `frame.pc`,
  продолжает `run_vm`. Деопт из середины выражения безопасен, т.к.
  регистры JIT транзитны, слоты — истина.
- Side-таблицы компилята: pc → offset машины для stackmaps/deopt-точек;
  в v1 deopt допускается только на границах инструкций байткода.

## 4. Файлы

```
src/jit/hotness.cr    # счётчики, порог, включение
src/jit/ir.cr         # IR-билдер (тонкий, над LLVM-валюes)
src/jit/compiler.cr   # Proto#packed → код (плюс side-таблицы)
src/jit/runtime.cr    # fun-хелперы, таблица адресов
src/jit/deopt.cr      # восстановление кадров
src/jit/emitter_*.cr  # (v2) собственный эмиттер
```

## 6.1 Сборка (M1+)

Бинарник линкуется с LLVM (`require "llvm"` в src/jit/compiler.cr):
нужны `LLVM_CONFIG=/opt/homebrew/opt/llvm/bin/llvm-config` и
`LIBRARY_PATH=/opt/homebrew/opt/llvm/lib` (rake подставляет их сам,
см. `build_clua!` в tasks/benchmark.rake). Совместимо: Crystal 1.21 ×
LLVM 23.1 (бенч-машина). Известные грабли opaque pointers LLVM 15+:
`Function#function_type`/`#return_type` сломаны — типы функций храним
рядом с декларациями (helper_types в compiler.cr).

## 7. Риски

- **llvm-шард vs системный LLVM** — проверяется первым (M1), откат на v2-эмиттер.
- **JIT-баги = SIGSEGV** — каждый класс опкодa гоняется диф-тестом
  против интерпретатора (тот же скрипт, два режима, diff stdout).
- **Известные miscompile при агрессивном тиринге** (LUA5_JIT_THRESHOLD=1,
  воспроизводятся на 15219d1 без M2.1; на дефолтном пороге 500 не
  проявляются, но этомины для долго живущих процессов): constructs.lua,
  db.lua, errors.lua, locals.lua, nextvar.lua, vararg.lua — assert-падения
  при компиляции всего подряд. Разобрать по классам перед M3.
- **GC-дисциплина** — инвариант 1.3 держим железно: тест с
  `GC.stress`-режимом (принудительная сборка на каждой аллокации).
- **Boehm-потолок на больших плотных таблицах** (замер 2026-11-08,
  array3d): 27M-слотовая таблица image → ~45% CPU в GC_mark_from на 12
  marker-потоках; GC_INITIAL_HEAP_SIZE/GC_FREE_SPACE_DIVISOR не помогают
  — цена не в частоте сборок, а в объёме консервативного mark-скана
  живого графа (16 байт/слот против 8 у LuaJIT, битовые паттерны чисел
  ретенятся как псевдоуказатели). array3d 28× от LuaJIT — целиком этот
  класс; лечение — unboxed-массивы чисел в таблицах и/или генерационный
  режим Boehm, не однодневная работа (тот же класс, что fasta).
- **Отладка** — режим `LUA5_JIT=trace`: лог компиляций, deopt'ов и причин.
- **Корутины** — v1: функции, исполняемые внутри корутины, не JIT-ятся
  (как в раннем LuaJIT); разрещение — в v2 со stitching.
- **Weak-таблицы и JIT-циклы** (M5.2): глобальный монотонный `weak_seen`
  + живые weak-таблицы включают tick на back-edge (gc каждые 32 рёбра —
  финализаторы могут бегать Lua). Прото с CLOSURE-опкодами (= возможные
  захваченные слоты) деоптится на weak-ребре: финализатор может записать
  upvalue-слот за спиной машинного кода. Без захватов tick безопасен —
  никто извне не может писать слоты кадра.
