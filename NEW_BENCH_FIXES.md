# NEW_BENCH_FIXES — sort-queue: диагноз и план фикса

Дата: 2026-11-08, rev `a2b5e9a`. Отчёт `rake benchmark:report`, min-of-3:
sort-queue — lua5.1 `2.004`, luajit `1.103`, clua `4.491` (4.1x от LuaJIT).

## 1. Диагноз

Профиль (perf, `/tmp/sq.perf`) + эксперименты:

| Замер                                             | Время    |
|---------------------------------------------------|----------|
| Полный бенч (`bin/lua5 bench/xray/sort-queue.lua 2000`) | ~4.8 с |
| Без `table.sort` (закомментированы оба вызова)     | ~1.4 с   |
| **Разница — сортировка**                           | **~3.4 с (~70%)** |

`merge_sort(2000)` × 1000 раундов ≈ **22M вызовов Lua-компаратора**.
Зонд `tmp/sortprobe.cr`: `Interp#call(less, [x, y])` из Crystal ≈
**160 нс/вызов** → 22M × 160 нс ≈ 3.5 с. Это практически весь отрыв.

### Причины по цепочке

1. **Компаратор всегда интерпретируется.** `table.sort`
   (`src/stdlib/table_lib.cr:73`) зовёт `i2.call(comp, [a,b])` →
   `run_vm` (`src/vm.cr:1214`) — полный вход в интерпретатор:
   Array аргументов + Array результатов + `Frame` + прогон байткода.
   У `less` нет цикла → OSR не срабатывает никогда.

2. **Tier-up до него не доходит.** Hotness-счётчик (`JIT.on_call`,
   `src/jit/hotness.cr:25`) инкрементируется только из CALL-опкода в
   диспетчере; вызовы через `run_vm` из нативного кода его не трогают.
   Проверено зондом: после 20M `Interp#call` — `hot=0`, `compiled? false`.
   В LuaJIT тот же компаратор — скомпилированный код, вызываемый из C.

3. **GC-шторм от merge_sort.** На каждый внутренний узел —
   `vals[0,mid]`, `vals[mid..]`, `out`, два `concat`-слайса (~10M
   массивов за прогон), плюс по 2 массива на каждый вызов компаратора
   (44M). В perf символы `GC_*` (mark_from, header_cache_miss, mutex) —
   около половины CPU; Boehm-маркеры (16 потоков) молотят непрерывно.
   `GC_MARKERS=1` не помогает (9.6 с) — проблема в объёме мусора.

## 2. Механизмы (ранжировано: эффект × риск)

### NBF1 — native→Lua вызов с tier-up и compiled-путём

Главный фикс, закрывает ~3/4 потерь. Механизм уже существует в
`jit_call_dispatch` (`src/jit/runtime.cr:261`) — переиспользовать:

1. В `Interp#call` (или на входе `run_vm`) для `LuaClosure` дёргать
   `JIT.on_call(self, cl0)` — нативные вызовы начнут считать hotness,
   компаратор тир-апнется после `THRESHOLD` (500) вызовов.
2. Если `cl.compiled` есть и выполнены те же гварды, что в
   `jit_call_dispatch` (`!@current_co && @hook_on == 0 &&
   num_params == argn && !vararg? && @jit_depth < 512`) — вызвать
   `JIT.raw_invoke(cp, self, cl, base, argn, want)` с аргументами,
   записанными на VM-стек, вместо входа в `run_vm`.
3. Любое несоблюдение условий/ошибка компиляции — старый путь
   `run_vm`, семантика не меняется (это критично: hooks, корутины,
   vararg, несовпадение арности должны идти по медленному пути
   ровно как сейчас).

Оценка: 22M × ~160 нс → ~30–50 нс (компилированный вызов + гварды) —
экономия ~2.5–3 с.

### NBF2 — безаллокационный вызов компаратора

Даже с NBF1 `Interp#call` платит за Array(args) + Array(results) на
каждый вызов. Для колбэков с фиксированной арностью добавить
специализированный вход уровня `Interp`:

```crystal
# один результат, аргументы пишутся прямо на VM-стек — ни одного Array
def call2(f : LuaValue, a : LuaValue, b : LuaValue) : LuaValue
```

и использовать его в замыкании `lt` внутри `table.sort`
(`src/stdlib/table_lib.cr:72–75`). Результат-Bool читать со стека,
`Lua.truthy` — на месте. Подходит и для `table.foreach`/`foreachi`,
`string.gsub`-колбэков (второй шаг, отдельно).

### NBF3 — merge sort без слайсов

Сортировка сейчас рекурсивная с копиями на каждом уровне. Заменить на
**восходящий (итеративный) merge sort с одним scratch-буфером**:
стабильность сохраняется (важно — комментарий в `table_lib.cr:143`:
стабильность держит дифтесты дружелюбными; Lua-сортировка
необязательна, но наши дифтесты опираются на детерминизм), аллокации —
один буфер размера n на вызов `table.sort` вместо ~10M массивов за прогон.
Это убирает GC-половину профиля.

## 3. Порядок работ и проверка

1. NBF1 → `crystal spec` (всё, особенно jit_spec) + зонд
   `tmp/sortprobe.cr` (ожидаю: `hot > 500`, `compiled? true`, время/вызов
   падает) → `rake benchmark:clua sort-queue`.
2. NBF2 на базе NBF1 → те же проверки.
3. NBF3 (независим от 1–2) → conformance + дифтест на сортировке
   (порядок равных элементов!) + бенчмарк.

Контроль результата: выход бенча неизменен
(`sort-queue 2000 143075067`, output_sha совпадает с lua5.1/luajit),
время — цель ≤ 2 с (сейчас 4.491): после NBF1+NBF2+NBF3 ожидание
~1.5–2 с, т.е. 1.4–1.8x от LuaJIT вместо 4.1x.

## 4. Вне скоупа

`xr-update` (481x) и `coro-mgr` (87x) — другой профиль (корутины/
виртуальные вызовы), не диагностировались здесь; NBF1/NBF2 могут
задеть их попутно, но мерить их надо отдельно.
